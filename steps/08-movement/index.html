Part 2 · Step 8

Movement and collision

Walking forward, strafing, and not walking through walls. With a grid map, collision is just “is there a wall cell under me?”, plus one small trick that makes it feel smooth instead of sticky.

Frame-rate independent movement

Monitors refresh at 60, 120 or 144 Hz, and frames sometimes take longer than usual. If we moved the player a fixed amount per frame, the game would run at different speeds on different machines. So every movement is a speed multiplied by dt, the seconds since the last frame:

rotatePlayer(p, TURN_SPEED * dt);         // radians per second × seconds
p.x += p.dirX * MOVE_SPEED * dt;          // cells per second × seconds

Our animate() helper also clamps dt to 50 ms. If the browser tab was in the background for 10 seconds, we don't want the player to teleport through the map on the first frame back.

Forward, back, and strafing

Forward is along d. For strafing we need the player's “right”, and we already have it: the camera plane p points right (step 3). Normalise it, since its length is tan(FOV/2), not 1:

let mx = p.dirX * forward + (p.planeX / planeLen) * strafe;
let my = p.dirY * forward + (p.planeY / planeLen) * strafe;
const len = Math.hypot(mx, my);   // forward + strafe together would be √2 faster…
const step = MOVE_SPEED * run * dt / len;   // …so divide it back to speed 1
tryMove(map, p, mx * step, my * step, radius);

Collision with a grid

Treat the player as a small square of half-size r (0.3 cells here). A position is legal if that square doesn't overlap any wall cell. Because walls are whole cells, we only need to check the few cells the square's corners fall into:

function isBlocked(map, x, y, r) {
  const x0 = Math.floor(x - r), x1 = Math.floor(x + r);
  const y0 = Math.floor(y - r), y1 = Math.floor(y + r);
  for (let cy = y0; cy <= y1; cy++)
    for (let cx = x0; cx <= x1; cx++)
      if (mapCell(map, cx, cy) !== 0) return true;
  return false;
}

Why a radius at all? Without one, you could put the eye right up against a wall, at t ≈ 0. The wall would project to an enormous height, its texture would be magnified into a few giant pixels, and the near side of the camera plane could even poke through. Keeping a little distance avoids all that.

Sliding along walls

The simplest response to a blocked move is to not move. Try that (untick “slide” below) and walk diagonally into a wall: you stop dead, which feels terrible. The fix is to try the two axes separately:

function tryMove(map, p, dx, dy, r) {
  if (!isBlocked(map, p.x + dx, p.y, r)) p.x += dx;   // x on its own
  if (!isBlocked(map, p.x, p.y + dy, r)) p.y += dy;   // then y on its own
}

When you push diagonally into a wall that runs north–south, the x part is blocked but the y part isn't, so you glide along the wall at reduced speed, the component of your motion parallel to it. That's what lets you take corners without getting stuck. It only works this neatly because walls are axis-aligned. Doom's arbitrary-angle walls need a real “project the motion onto the wall line” step, which is a dot product (step 1 again).

  • Turn off sliding and try to walk along a corridor wall at a slight angle.
  • Set the radius to 0.05 and walk face-first into a wall. That's what the radius protects you from.
  • A radius of 0.49 makes a one-cell corridor barely passable. Above 0.5 it would be impossible.
There's one subtle bug class we avoid by keeping steps small: if a single move were longer than the player's size, you could jump over a thin wall (“tunnelling”). Our speed is at most 5.4 cells/s and dt is clamped to 0.05 s, so a step is at most 0.27 cells and that can't happen with whole-cell walls.

70 Hz tics and ClipMove

Wolfenstein's game logic counts time in tics of 1/70 of a second, matching the VGA refresh rate. Each frame it measures how many tics have passed and multiplies all movement by that, which is the same frame-rate independence as our dt. On a slow 386 you might get 10 frames per second, but you'd still cross a room in the same time, just in bigger jumps.

Collision lives in ClipMove and TryMove. The player is a box of half-size PLAYERSIZE = MINDIST = 0x5800 in 16.16 fixed point, about 0.34 tiles, close to our 0.3. TryMove checks the tiles under the box's corners (plus nearby actors). If the full move fails, ClipMove tries only the x part, then only the y part. That's our sliding, line for line. Strafing was there too: hold Alt and the arrow keys sidestep instead of turning.
