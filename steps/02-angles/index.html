Part 1 · Step 2

Angles, sine, cosine and rotation

The player has a position and a facing direction. Pressing ← or → turns them. This step covers how to turn an angle into a direction vector and back, and how a 2 × 2 rotation matrix turns a vector without ever storing an angle.

From angle to direction

Put a unit vector at angle θ, measured from the +x axis. Its tip lies on the unit circle, at

dir(θ) = (cos θ, sin θ)

That is all cosine and sine are here: the x and y components of a unit vector pointing at angle θ. Angles are in radians (a full turn is 2π ≈ 6.283). JavaScript's Math.cos and Math.sin expect radians, and so does every formula below.

Because our y axis points down, a growing θ sweeps clockwise on screen. θ = 0 faces east, θ = π/2 faces south (down the map), θ = π faces west. Turning right means increasing the angle.

And back again

Given a vector (x, y), its angle is Math.atan2(y, x). The two-argument arctangent looks at both signs, so it gets the quadrant right, which a plain atan(y / x) can't. We'll use it to point the camera at whatever you drag in the demos.

Rotating a vector

To turn the player by an angle α, we could store the facing angle θ, add α, and recompute (cos θ, sin θ). That works. But in the next step the camera gets a second vector (the screen plane), and later we'll want to rotate arbitrary points into camera space. The general tool is the rotation matrix.

A linear transformation is completely determined by what it does to the two basis vectors (1, 0) and (0, 1). Rotating by α sends

  • (1, 0) → (cos α, sin α) (by definition of cos/sin), and
  • (0, 1) → (−sin α, cos α) (the first one, turned a further 90°; that's perp from step 1).

Those images become the columns of the matrix:

R(α)=cos⁡α−sin⁡αsin⁡αcos⁡αR(α)⋅vxvy=cos⁡α−sin⁡αsin⁡αcos⁡αvxvy=vx⁢cos⁡α−vy⁢sin⁡αvx⁢sin⁡α+vy⁢cos⁡α

In code, this is the function the engine uses to turn the player:

function rotate(v, a) {
  const c = Math.cos(a), s = Math.sin(a);
  return { x: v.x * c - v.y * s,
           y: v.x * s + v.y * c };
}

Useful properties:

  • Rotations compose by adding angles: R(α)·R(β) = R(α + β). Turning a little bit every frame is just applying a small rotation every frame.
  • Lengths and angles between vectors are preserved. If the direction vector and the screen plane vector are perpendicular before the rotation, they stay perpendicular.
  • The inverse is the transpose: R(α)−1 = R(−α) = R(α)T. Undoing a rotation is free. Keep this one in mind for step 3.
One practical wrinkle: if you rotate a vector by small amounts thousands of times, floating-point rounding slowly changes its length. For our purposes (minutes of play) the drift is invisible, but a real engine either re-normalises occasionally or does what the originals did: store an integer angle and look up sin/cos in a table every frame.
  • Set θ = 90°. The direction points down, and the matrix becomes [0 −1; 1 0], which is exactly perp.
  • Pick “8 angles” and drag around: the direction snaps. That's what a too-small lookup table would feel like when turning.
  • Watch |R·v|: it always equals |v|.

Sine tables and binary angles

Computing a sine in software on a 386 takes hundreds or thousands of cycles. Looking one up in an array takes a handful. So both engines precompute tables at startup and never call a sine function during play.

  • Wolfenstein 3D stores the player's angle as an integer in degrees (ANGLES = 360) and has a sintable of fixed-point values. The cosine table is the same array, offset by a quarter turn (cos θ = sin(θ + 90°)). The ray caster uses a finer table of FINEANGLES = 3600 steps (a tenth of a degree) for tangents.
  • Doom uses binary angle measurement: an angle is an unsigned 32-bit integer where 232 is a full circle. Adding two angles wraps around automatically on overflow, so there's no “if angle ≥ 360 then subtract 360” anywhere. The top bits index an 8192-entry finesine table.

Try the “angle table” dropdown above: with 360 entries the snapping is already invisible at this size, and 3600 is plenty for casting 320 rays.
