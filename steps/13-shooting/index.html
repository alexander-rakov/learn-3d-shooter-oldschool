Part 3 · Step 13

Shooting and enemies

Time to make it a game. Shooting turns out to be a ray cast you already know, aimed through the middle of the screen. The robots need eyes (another ray cast), ears (a flood fill), legs (walking from cell to cell, opening doors) and a small brain: a state machine written as a table, the way Wolfenstein did it.

Hitscan: the bullet is a ray

Wolfenstein's guns don't fire projectiles that fly through the air. A shot hits instantly, along the line you're looking down. Games call this hitscan. For us, that line is the ray through the centre column of the screen, and we already know what it hits: the wall at depth zBuffer[W/2], unless a robot is in the way.

For each robot, step 11's camera space gives its depth v and sideways offset u. It's a candidate if it's in front of us and nearer than that wall. But is the crosshair actually on it? The centre ray is c = 0, the straight-ahead ray d. It passes the robot's picture u · |p| cells to the side of the picture's middle, and the picture is one cell wide. That gives the texture column directly:

texX = 64 · (0.5 − u · |p|)

The texture row is even simpler. Sprites are centred on the horizon and the crosshair is on the horizon, so the centre of the screen always looks at texture row 32, whatever the distance. A hit is one texel lookup:

for (const a of game.actors) {
  if (!isAlive(a)) continue;
  const { u, v } = toCameraSpace(p, a.x, a.y);
  if (v < NEAR_PLANE || v >= wallDepth) continue;          // behind us, or behind the wall
  const texX = Math.floor(TEX * (0.5 - u * planeLen));
  if (texX < 0 || texX >= TEX) continue;
  if (!actorImage(a, p).pixels[texX * TEX + TEX / 2]) continue;   // a transparent texel
  if (!best || v < best.v) best = { actor: a, v, texX };  // the nearest one takes the bullet
}

So a shot between a robot's legs or past its arm really does miss. That's stricter than Wolfenstein, which counted anything close to the centre of the screen.

Dice from a table

How much damage a hit does is random. Our random numbers come from a fixed table of 256 bytes, read one after another, as in Wolfenstein and Doom. It's fast, and it makes the game repeatable: the same inputs give the same rolls.

The damage rule is Wolfenstein's own. Distance is counted in whole cells, as the larger of the x and y differences:

if (dist < 2)      damage = rnd() / 4;              // point blank: 0 … 63
else if (dist < 4) damage = rnd() / 6;              // 0 … 42
else if (rnd() / 12 < dist) missed;                 // far away: the farther, the likelier to miss
else               damage = rnd() / 6;

A robot has 25 hit points, so up close one shot usually does it, and from across a room it takes two or three, plus the misses.

Eyes: line of sight

Can a robot see you? Draw a line from it to you and check nothing solid is in the way. That's a ray cast, and castRay already handles walls and doors. The trick is the direction: cast from the robot with direction b − a, the vector from robot to player, not a unit vector. Measured along that vector, t = 1 is exactly where you stand, so

function canSee(map, ax, ay, bx, by) {
  return castRay(map, ax, ay, bx - ax, by - ay).t >= 1;   // the first wall is beyond b
}

A closed door blocks the line and a half-open one only through its gap, because castRay already knows about doors. A robot that's standing guard also only looks ahead. You must be in front of it, which is the sign of a dot product, as in step 1: (you − robot) · facing > 0. Sneak up from behind and it won't notice you, until you make a noise.

Once it notices you, it doesn't react instantly: a random reaction time of 0.15–0.65 seconds is your window to shoot first.

Ears: sound goes through open doors

When you fire, every robot that could hear it wakes up. Sound travels across open floor and through doors that aren't fully shut, but not through walls or closed doors. Finding everywhere it reaches is a flood fill, the paint bucket of a paint program: start at the player's cell, and keep spreading to neighbouring cells that are floor or open doors.

const stack = [start];
while (stack.length) {
  const i = stack.pop();
  for (const n of [i - 1, i + 1, i - map.w, i + map.w]) {   // left, right, up, down
    if (reached[n]) continue;
    const cell = map.cells[n];
    if (cell === 0 || (cell === DOOR && map.doors.get(n).open > 0)) {
      reached[n] = 1;
      stack.push(n);
    }
  }
}

Every robot standing in a reached cell has heard you. That's why opening a door is the dangerous moment in Wolfenstein: fight with the doors shut and the next room stays asleep.

Legs: walking from cell to cell

A chasing robot walks from the centre of one cell to the centre of a neighbouring one, and only decides where to go next when it arrives. To choose, it scores the 8 directions by how directly they point at the player (the dot product again) and takes the best one that's free. Free means: no wall or blocking object, no other robot standing there or walking there, not the player's cell, and no cutting diagonally past a corner. Turning straight back is the last resort, so a robot doesn't dither between two cells.

A door counts as free: the robot opens it and waits until it's fully open. And because a robot heading into a door cell counts as “occupying” it, the door won't close on it. That's the same isOccupied hook step 12 used for the player.

This isn't real path finding. A robot on the far side of a long wall will happily walk into it forever. Wolfenstein's guards are no smarter, and somehow it still works.

A brain: the state machine as a table

A robot is always in one of a few states. Each state says which picture to show, how long it lasts, what to do every frame (think), what to do once on entering (action), and which state comes next. The robot's whole behaviour is this table plus the functions it names:

const ROBOT_STATES = {
  stand: { frame: 'stand', think: thinkStand },
  chase: { frame: 'walk',  think: thinkChase },
  aim:   { frame: 'aim',   time: 0.35, think: faceThePlayer, next: 'shoot' },
  shoot: { frame: 'shoot', time: 0.15, action: robotShoots, next: 'aim2' },
  aim2:  { frame: 'aim',   time: 0.3,  next: 'chase' },
  pain:  { frame: 'pain',  time: 0.3,  next: 'chase' },
  die1:  { frame: 'die1',  time: 0.12, next: 'die2' },
  die2:  { frame: 'die2',  time: 0.12, next: 'die3' },
  die3:  { frame: 'die3',  time: 0.16, next: 'dead' },
  dead:  { frame: 'dead' },
};
          sees or hears you                a clear shot, by chance
  stand ─────────────────────▶ chase ─────────────────────────▶ aim ─▶ shoot ─▶ aim2 ─┐
                                 ▲                                                     │
                                 └─────────────────────────────────────────────────────┘
  any state ── hit ──▶ pain ──▶ chase          hp ≤ 0 ──▶ die1 ─▶ die2 ─▶ die3 ─▶ dead

Running it is a few lines: call think, and when the state's time is up, switch to next and run its action. Adding a new kind of enemy, or a new trick for this one, means adding rows rather than rewriting logic.

While chasing with a clear line to you, a robot has a small chance every frame to stop and shoot, larger when it's closer. The shot itself follows Wolfenstein's rule for enemy fire: a hit chance out of 256 of 160 − 8 · dist, or 160 − 16 · dist if you're running, then a damage roll of rnd()/8, /16 or /32 depending on distance. (That's half of Wolfenstein's damage, to keep the demo forgiving.)

The pictures follow the state. Standing and walking use step 11's 8 rotations. Aiming, shooting, pain and dying use a single front-facing picture each, because in those states the robot has turned to face you anyway.

  • Robot 1 faces the first door. Open it and wait a moment: you'll see its reaction time in the log before it starts moving.
  • Fire with all doors closed, then with one open, and watch how far the blue flood spreads. Robots outside it keep standing.
  • Aim between a robot's legs or just past its arm. The log says “nothing under the crosshair”.
  • Hold Shift while robots shoot at you: running lowers their hit chance, which the log shows as a smaller number to beat.
  • Stand still in a doorway. Robots will open doors to get to you.

statetype, ears made of areas, and a table of random numbers

Wolfenstein's enemies are driven by exactly this kind of table. Each state is a statetype record: a rotate flag (does this picture come in 8 directions?), the picture number, a duration in tics (1/70 s), a think function, an action function and a pointer to the next state. A guard has a few dozen of them (s_grdstand, s_grdchase1, …), linked into the same loops as our table.

Random numbers come from US_RndT(), which steps through a fixed 256-byte table. Doom kept the idea (P_Random in m_random.c), and it's what makes Doom's recorded demos work: replay the same key presses and the same “random” rolls follow.

Shooting (GunAttack) picks the closest visible enemy within a few pixels of the screen centre, checks the line of sight with CheckLine, which walks the tile map, and rolls the damage exactly as above. Enemies shoot back in T_Shoot with a hit chance that falls with distance and with how fast you're moving.

Hearing works by areas. The level designer paints every floor tile with an area number, and doors sit between areas. The game keeps a matrix of how many open doors join each pair of areas. When you fire, it sets madenoise, and any guard in an area connected to yours wakes up. It's our flood fill, worked out in advance. Some guards were placed in “ambush” mode: they ignore sounds and wait until they see you.

Chasing is tile-to-tile too. SelectChaseDir tries the diagonal towards the player first, then the two straight directions, then the old direction, then random ones, and only turns straight back if nothing else works. An occupancy grid (actorat) keeps two actors out of one tile.
