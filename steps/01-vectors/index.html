Part 1 · Step 1

Vectors and coordinates

Everything a Wolfenstein-style engine does (moving the player, casting rays, projecting walls) comes down to a handful of operations on 2D vectors. This step sets up the coordinate system and the vector toolbox used for the rest of the series.

The world is a flat grid

A Wolfenstein 3D level is a 2D map, 64 × 64 cells, where each cell is either empty or a solid cube of wall. There is no “up” in the world data at all: every wall is the same height, and the floor and ceiling are flat. The third dimension only appears at the very end, when we draw.

So our world coordinates are two numbers, (x, y), measured in cells:

  • x grows to the right, y grows downward. That's the same orientation as screen pixels and as a map stored in rows (map[y][x]), so the top-down diagrams and the map data line up with no flipping.
  • One unit = one cell. The point (3.5, 2.5) is the centre of the cell in column 3, row 2. The cell containing a point is (floor(x), floor(y)).
Because y points down, the coordinate system is “left-handed” compared to the maths-textbook one. The only visible consequence: positive angles turn clockwise on screen. We'll meet that in step 2.

Points and vectors

Both are pairs of numbers, but they mean different things. A point is a location (where the player stands). A vector is a displacement (which way the player faces, how far a ray travelled). Point − point = vector; point + vector = point.

In the demos we write them as small objects:

const add   = (a, b) => ({ x: a.x + b.x, y: a.y + b.y });
const sub   = (a, b) => ({ x: a.x - b.x, y: a.y - b.y });
const scale = (a, k) => ({ x: a.x * k,   y: a.y * k });
const dot   = (a, b) => a.x * b.x + a.y * b.y;
const len   = (a)    => Math.hypot(a.x, a.y);           // √(x² + y²)
const norm  = (a)    => scale(a, 1 / len(a));          // same direction, length 1
const perp  = (a)    => ({ x: -a.y, y: a.x });         // rotated 90°

In the engine itself (from step 5 on) we'll unpack vectors into plain variables like dirX, dirY. That avoids creating objects in the inner loops, and it's also how the original C code looked.

The three operations that matter

1. Addition and scaling: moving along a direction

If the player stands at pos and faces unit vector d, then pos + t·d is the point t cells straight ahead. Walking forward is pos = pos + speed·dt·d. Casting a ray is the same formula with a growing t. This one expression, P(t) = pos + t·dir, is the heart of a raycaster.

2. Length and normalisation

len(v) is the Euclidean distance (Pythagoras). A unit vector has length 1 and represents a pure direction. norm(v) divides by the length to get one. We'll mostly keep the facing direction normalised, so that “t units along it” really means t cells.

3. The dot product: “how much of a is along b”

a · b = axbx + ayby = |a| |b| cos θ

where θ is the angle between the vectors. Three things follow that we'll use a lot:

  • If b is a unit vector, a · b is the length of the projection of a onto b: the shadow a casts on b's line. This is exactly “how far in front of me is that point”, which is the depth we need for perspective (step 6) and for the fisheye fix (step 7).
  • The sign says front or back: positive means less than 90° apart, negative means pointing away. “Is the enemy in front of me?” is one dot product.
  • Zero means perpendicular.

Bonus: the perpendicular

perp(a) = (−a.y, a.x) is a rotated by 90°. Check it: the dot product a.x·(−a.y) + a.y·a.x = 0. With y pointing down, this rotation is clockwise on screen. In other words, if a is where you're looking, perp(a) points to your right. Step 3 builds the camera's “screen plane” from exactly this vector.

  • Make a · b exactly zero. The projection collapses to the origin.
  • Turn on perp(a) and rotate a: perp always stays 90° clockwise (to the “right” of a).
  • Make a length 1 (|a| = 1.00). Now the projection length is just a · b.

No floating point: fixed-point numbers

Our JavaScript uses 64-bit floats for everything, and that's fine. In 1992 it wasn't. The 386 had no floating-point unit (the 387 math coprocessor was an expensive extra), and even with one, float maths was far slower than integer maths. So Wolfenstein 3D and Doom store every coordinate as a fixed-point integer: a 32-bit value whose low 16 bits are the fraction. This is called “16.16” format.

value_fixed = round(value × 65536)        // 1.0 is 0x00010000
a + b  →  a_fixed + b_fixed               // addition is just integer addition
a × b  →  (a_fixed × b_fixed) >> 16       // the product has 32 fraction bits; shift 16 away

The low 16 bits count 65536ths, not hundredths

It's tempting to read 3.75 as “3, then 75”. But the fraction isn't stored as decimal digits. The low 16 bits hold a whole number of 1/65536 steps, so a fraction f is stored as f × 65536:

3.75 × 65536 = 245760 = 0x0003C000
                         ^^^^ ^^^^
                         |    low 16 bits:  0xC000 = 49152,  49152 / 65536 = 0.75
                         high 16 bits: 0x0003 = 3

In binary it's even clearer, because the bits after the “binary point” are worth ½, ¼, ⅛, and so on:

0.75 = ½ + ¼   →  binary 0.11  →  the 16 fraction bits are 1100 0000 0000 0000 = 0xC000
0.5            →  binary 0.1   →  1000 0000 0000 0000 = 0x8000
0.1            →  0.000110011001100…  (repeats forever, so it gets rounded: 0x199A)

That's also why some decimals can't be stored exactly: 0.1 has no finite binary expansion, just as ⅓ has no finite decimal one. (Floats have the same problem, only with more bits.)

Negative numbers use ordinary two's complement on the whole 32-bit value, so the split reads slightly oddly: −1.2 becomes 0xFFFECCCD. The high half is −2 and the low half is +0.8, and −2 + 0.8 = −1.2. The integer part is always rounded down (toward −∞), and the fraction is always a positive amount added on top. The calculator below shows the split.

In Wolfenstein's source, one map cell is TILEGLOBAL = 1<<16, so the integer part of a coordinate is the cell index and the fraction is the position inside the cell. Doom calls the same idea FRACUNIT and multiplies with a small assembly routine, FixedMul, because the intermediate product needs 64 bits.

Notice that −1.2 can't be stored exactly: the nearest 16.16 value is off by about 0.000006. That's small, but these errors pile up. In the originals they show up as walls that “wobble” by a pixel when you stand very close.
