Part 3 · Step 14

HUD, weapon and pickups: a floor you can finish

The engine is done; this step is about everything drawn on the screen rather than in the world: a status bar, a gun in your hand, flashes when you get hurt or pick something up. Add things to pick up, a key, a locked door and an exit, and it's a game. The demo at the bottom is one complete floor.

Making room for a status bar

The framebuffer is still 320 × 200, but the 3D view now gets only the top 160 rows; the bottom 40 are the status bar. The renderer doesn't need to know. Pixels are stored row after row, so the first 160 rows are simply the first 320 × 160 entries of the array, and a typed array can give us a view of them without copying anything:

function subScreen(screen, h) {
  return { w: screen.w, h, pixels: screen.pixels.subarray(0, screen.w * h), present() {} };
}
const view = subScreen(screen, 160);
renderFrame(view, map, player, …);   // h = 160: the horizon moves up to row 80

After the world is drawn into view, everything else is painted on top in order: the weapon, any flash, text, the status bar. Then the whole framebuffer goes to the canvas in one putImageData.

Text without a font file

The status bar needs letters and digits. A 5 × 7 pixel font is small enough to write by hand: each glyph is 7 rows of 5 bits, and each row is a number. Here's the zero:

'0': '0e11131519110e'      0e  .###.
                           11  #...#
                           13  #..##       bit 4 (0x10) is the leftmost pixel,
                           15  #.#.#       bit 0 the rightmost
                           19  ##..#
                           11  #...#
                           0e  .###.

Drawing a character tests each bit and fills a scale × scale block where it's set. The status bar uses scale 1 for labels and scale 2 for the big amber numbers. A second pass in black, offset by one block, gives every letter a drop shadow. 46 glyphs cover everything the game ever says.

A weapon in your hand

The gun is a sprite, but not a sprite in the world. It doesn't have a position or a depth, and the camera transform doesn't apply: it's pasted flat onto the bottom centre of the view at a fixed size, after everything else, so nothing can cover it. The drawing loop is the sprite column loop from step 11 with the camera taken out: step through the texels, skip transparent ones.

Two touches make it feel alive. Firing shows three pictures in quick succession: the muzzle flash, then the gun kicked down by the recoil, then easing back. And walking makes it sway. A bob phase grows with the distance you walk, and the gun's offset is

x = 7 · cos(bob)     y = 6 · |sin(bob)|

The |sin| bounces once per step while the cos swings left and right once per two steps, so the gun traces a small arc, like a hand moving with your stride. Stand still and it stops, because the phase only changes when you move.

Flashes

Getting hit flashes the view red; picking something up flashes it gold. Each pixel is blended towards the flash colour by an amount a that fades back to zero over a fraction of a second:

c′ = c + (target − c) · a    for each of red, green and blue

That's 51,200 pixels times three channels, a few times per second. Easy for us. Step 9's 1992 box explains why Wolfenstein didn't have to do any of it.

Pickups, keys and the exit

Pickups are sprites that don't block you. Each frame, any pickup within half a cell of you is taken, if it's any use: a medkit stays on the floor while your health is full, and so does ammo while you're carrying the maximum. What each one does is a small table, in the same spirit as step 13's state table:

const PICKUPS = {
  medkit: { text: 'MEDKIT', sound: 'pickup', take(g) { if (g.health >= 100) return false; g.health += 25; … } },
  ammo:   { text: 'AMMO BOX', sound: 'pickup', take(g) { … g.ammo += 8 … } },
  clip:   { text: 'AMMO CLIP', … },                       // dropped by robots when destroyed
  coins:  { text: 'GOLD COINS', treasure: true, take(g) { g.score += 100; return true; } },
  gem:    { text: 'A GEM!', treasure: true, … },
  key:    { text: 'THE GOLD KEY', take(g) { g.hasKey = true; return true; } },
};

Locked doors are doors with a flag (I and = in the map, drawn with gold bands and a keyhole). useAction takes a canOpen(door) callback; the game answers “only with the key”. Robots treat locked doors as walls.

The exit is a wall, texture 9, a switch in a hazard-striped frame. Using it flips it to its “on” picture and ends the floor with Wolfenstein-style percentages: robots destroyed, secrets found and treasure collected.

Extras

Sound, from scratch

No sound files either. The browser's Web Audio API can make sound from oscillators (a sine, square or sawtooth wave at a frequency you choose) and from noise, run through a filter. Every effect is one or two of those with a quick fade-out:

shoot: () => { noise(0.2, 4000, 250, 0.8); tone('sine', 150, 45, 0.16, 0.7); },
                 // a hiss falling from 4 kHz to 250 Hz, plus a low thump falling 150 → 45 Hz
alert: () => notes('square', [880, 660], 0.08, 0.08, 0.18),   // two beeps

Sounds made by robots get quieter with distance: volume 1 / (1 + 0.25·d).

An automap for free

Press M for a map of everywhere you've seen. Rendering already visits every cell the rays pass through, so castRay marks them in a seen array as it goes. That's step 11's spotvis, kept for the whole level instead of cleared each frame. The map draws seen cells from above, and what you haven't looked at stays black.

Mouse look

Tick “mouse look” and click the view: the browser's pointer lock hides the cursor and reports raw mouse movement. Each pixel of sideways movement turns you by 0.004 radians with the same rotatePlayer the arrow keys use, and the mouse button fires. Esc gives the pointer back.

Light falloff

Tick “light falloff” and far things get darker: each colour is scaled by k = max(0.15, 1 − depth/14). It's cheap for the same reason everything else in this engine is cheap: depth is constant along a wall column, along a floor row, and across a sprite. So k is computed once per column, per row or per sprite, never per pixel. This is the idea behind Doom's lighting, which Part 4 will look at.

  • Walk and watch the gun: it swings in an arc with your steps and stops when you stop.
  • Try the locked door before you have the key, then again after.
  • Turn on light falloff and look down the hall. Then look at the readout's frame time: the whole frame, with everything on this page, typically takes a millisecond or two.
  • Open the map early, then again after exploring. Rooms appear only once you've looked into them.
  • For 100% secrets: one wall in the west room isn't a wall.

A face in the status bar, and palette tricks

Wolfenstein's status bar shows the floor, score, lives, health, ammo, keys and weapon, plus the most famous part: the hero's face, which looks around, gets bloodier as health drops, and grins when you pick up a new gun. The bar is only redrawn when a number changes, which matters when every screen write goes over a slow bus to video memory.

The weapon is drawn last, at a fixed size, by a simple scaler that ignores the depth buffer, just like ours. It doesn't bob: in Wolfenstein the gun stays still while you walk. Doom made it sway.

The red and gold flashes are palette tricks, as step 9 mentioned. Instead of touching any pixels, the game reprograms the VGA's 256 palette entries for a few frames, and the whole screen changes colour at once, for free.

Items are picked up when you enter their tile (GetBonus), and a medkit or food is left alone at full health, which our take returning false copies. The end-of-floor screen tallies kill, secret and treasure ratios against a par time, with a bonus for each 100%.

Sound came from the AdLib or Sound Blaster card: short digitized samples for gunshots and shouts, synthesized FM music, and PC speaker beeps as a fallback. Our oscillators sit somewhere between the PC speaker and FM synthesis.

What we have, and what's next

That's Part 3, and with it a complete, if small, Wolfenstein-style game: ray-cast walls with textures, floors and ceilings, sprites with 8 directions, doors and secret walls, enemies that see, hear and chase, hitscan shooting, pickups, a status bar, sound and an automap. Every texture, sprite, letter and sound is generated by the code you can read in these files.

The grid has served us well, but it's also the limit: every wall is axis-aligned, every room is the same height, and the floor is always flat. A year after Wolfenstein, Doom threw the grid away. Part 4 looks at how: polygons instead of cells, walls at any angle, floors at any height, and a BSP tree to draw them in the right order.
