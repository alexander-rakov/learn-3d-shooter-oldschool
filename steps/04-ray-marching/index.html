Part 1 · Step 4

The grid, and the naive way to find a wall

Each ray has to answer one question: how far do I travel before I enter a wall cell? Here's the obvious answer, small steps until you bump into something, and the two reasons no 1992 engine could afford it.

The map

The level is a grid of numbers: 0 for empty, anything else for a wall (the number later picks the texture). We write maps as strings because they're easy to edit, and store them as a flat array indexed by y * width + x:

const map = parseMap([
  '############',
  '#..........#',
  '#..##...#..#',
  '#...#......#',
  '#.......##.#',
  '#..#.......#',
  '#......#...#',
  '############',
]);

function isWall(map, x, y) {
  const cx = Math.floor(x), cy = Math.floor(y);         // which cell is (x, y) in?
  if (cx < 0 || cy < 0 || cx >= map.w || cy >= map.h) return true;  // outside = solid
  return map.cells[cy * map.w + cx] !== 0;
}

Ray marching

A ray is P(t) = pos + t·dir (step 1). The simplest way to find where it hits: start at t = 0, take a small step, check the cell, repeat.

function marchRay(map, posX, posY, dirX, dirY, stepSize) {
  const len = Math.hypot(dirX, dirY);
  dirX /= len; dirY /= len;                 // unit direction: t is now distance in cells
  for (let t = 0; t < 50; t += stepSize) {
    if (isWall(map, posX + t * dirX, posY + t * dirY)) return t;
  }
  return Infinity;
}

It works. Play with the step size below and you'll find two problems.

Problem 1: accuracy

The march stops at the first sample inside a wall, which can be up to one step past the true surface. That error goes straight into the wall's distance, and so into its height on screen. With steps of 0.3 cells, walls shimmer and bulge as you move.

Worse, a ray that only clips the corner of a wall cell can step right over it and report a wall further away, or none at all. Turn on the fan, set a big step size, and look at the corners.

Problem 2: cost

The fix for accuracy is smaller steps, and the cost goes up in proportion. A wall 10 cells away needs 1,000 checks at a step of 0.01, and we need 320 rays per frame. That's 320,000 map lookups per frame, about ten million per second at 30 fps. On a 1992 PC that's out of the question. (Even today it's wasteful.)

The key observation

Look at the grid. A ray can only enter a new cell at the moment it crosses a grid line. Between two crossings it stays in the same cell, so all the samples in between are wasted. If we could jump from one grid line crossing to the next, we'd check exactly the cells the ray passes through, no more and no fewer, and find the exact point where it enters the wall.

That's the algorithm in the next step.

The cycle budget

A 386 at 25 MHz runs roughly 25 million clock cycles per second, and a simple instruction takes a few cycles. At 30 frames per second that's under a million cycles per frame for everything: game logic, sound, casting 320 rays, and writing 64,000 pixels to the screen. That leaves a few thousand cycles per column. A ray march with hundreds of steps per ray doesn't fit. Wolfenstein was designed for exactly this budget, with every inner loop hand-written in assembly.

Ray marching isn't dead, by the way: modern “signed distance field” renderers march rays with variable step sizes, using a distance function to know how far it's safe to jump. Same idea, smarter step.
