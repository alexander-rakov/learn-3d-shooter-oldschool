Part 2 · Step 10

Floor and ceiling casting

Walls are drawn in vertical columns, because every point in a wall column is at the same depth. Floors are the other way round: every pixel in a screen row sees the floor at the same depth. So we draw them row by row, and use the camera matrix to go from a pixel to a point on the floor.

One row, one depth

Back to the side view from step 6. The eye is at height EYE_HEIGHT = 0.5 above the floor. A pixel row that is r rows below the horizon looks down at the floor along a line that drops r / projScale per unit of depth, by the same similar triangles as before. It reaches the floor, 0.5 below the eye, at depth

rowDist = EYE_HEIGHT · projScale / r

Sanity check: a wall at depth z has its bottom edge projScale / z / 2 rows below the horizon. Plug that in for r and rowDist = z. The floor meets the wall exactly where the wall ends. Rows near the horizon (small r) are far away; the bottom row is closest.

The ceiling is the mirror image: row h − 1 − y is as far above the horizon as row y is below it, so it has the same rowDist, and it's directly above the same floor point. One computation serves both.

From pixel to world point: the camera matrix

Inside a row, pixel x looks along the same ray as the wall column x: d + c·p, with c = 2x/W − 1. Going a depth of rowDist along it (remember from step 7: t along a plane ray is depth), the floor point is

world=pos+rowDist⋅(d+c⋅p)=pos+rowDist⋅pxdxpydyc1

That's the camera matrix from step 3, used forwards. In step 3, M⁻¹ took a world point to camera coordinates (u, v) so we could find its pixel. Here M takes camera coordinates, (c·rowDist, rowDist), back to the world so we can find what a pixel shows. Same matrix, opposite directions: world → screen for objects, screen → world for surfaces.

Linear along the row

For a fixed row, rowDist is constant, and world is a linear function of c. Moving one pixel right changes c by 2/W, which moves the world point by the constant vector rowDist · p · 2/W. So, exactly like the wall's texPos += step, each pixel costs two additions:

for (let y = h / 2; y < h; y++) {
  const rowDist = EYE_HEIGHT * projScale / (y + 0.5 - h / 2);
  let fx = p.x + rowDist * (p.dirX - p.planeX);      // world point at c = -1 (x = 0)
  let fy = p.y + rowDist * (p.dirY - p.planeY);
  const stepX = rowDist * 2 * p.planeX / w;          // world step per pixel
  const stepY = rowDist * 2 * p.planeY / w;

  for (let x = 0; x < w; x++) {
    const tx = ((fx * TEX) | 0) & (TEX - 1);         // fractional part × 64
    const ty = ((fy * TEX) | 0) & (TEX - 1);
    pixels[y * w + x]           = FLOOR_TEXTURE[tx * TEX + ty];
    pixels[(h - 1 - y) * w + x] = CEILING_TEXTURE[tx * TEX + ty];
    fx += stepX;  fy += stepY;
  }
}

The texture lookup is the neatest part. A floor tile covers exactly one map cell, so the texture coordinate is just the fractional part of the world position × 64. & 63 keeps the low six bits, which is the same as “mod 64” for a power of two. The tile repeats in every cell for free.

Draw order

We fill the whole floor and ceiling first, then draw the wall columns on top. That's simple but wasteful: every pixel behind a wall gets a floor texel that's immediately overwritten. A tighter engine would draw floor only below each column's bottom. For 320 × 200 in JavaScript it doesn't matter, but in 1992 it was exactly the kind of thing that did.

  • Hover pixels in the same row: rowDist doesn't change, only c does. Hover just below the horizon: rowDist shoots up.
  • Look at the far floor: the tile borders turn into flickering noise. That's aliasing again, much worse than on walls because each pixel steps across many texels. It's why later engines filtered or mipmapped textures.
  • Toggle the flat mode to see Wolfenstein's look: arguably clearer, and much cheaper.

Wolfenstein didn't do this. Doom did, sideways.

Wolfenstein 3D's floor and ceiling are solid colours, cleared before the walls are drawn (step 6). Texturing them costs a texture lookup for most of the screen, which a 386 couldn't afford on top of everything else. Raycasters that came soon after, such as Blake Stone: Aliens of Gold (1993), added textured floors and ceilings using row-by-row casting like ours.

Doom draws its floors (“visplanes”) the same way: as horizontal spans, runs of pixels in one screen row, because a row of a horizontal surface has constant depth. Its R_MapPlane computes the distance for the row from a table, steps through the flat's texture with fixed-point increments, and uses the distance to pick a lighting level. Part 4 of this series will get there. The basic trick, “constant depth along a row, so step linearly”, is the one you've just seen.

What we have, and what's next

That's the end of Part 2. From two vectors and a grid we've built a complete Wolfenstein-style renderer: exact ray casting, correct perspective, collision, and textured walls, floor and ceiling, all in about 300 lines of engine code.

What's missing is everything that makes it a game: objects and enemies (sprites, which need the camera-space transform from step 3 and a depth buffer), doors, and shooting. That's Part 3, starting with sprites.
