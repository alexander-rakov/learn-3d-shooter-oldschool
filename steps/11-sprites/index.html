Part 3 · Step 11

Sprites: objects and enemies

A world made only of walls is a maze, not a place. Barrels, lamps and enemies in Wolfenstein are sprites: flat pictures that always face the camera. Placing one on screen is the camera-space transform from step 3. Drawing it is a scaled wall column with holes in it. Hiding it behind walls takes one number per screen column.

Billboards

A sprite is a picture standing upright at a point on the floor, turned to face the camera, whichever way the camera looks. That sounds like a cheat, and it is, but it's a very good one. Because the picture is always parallel to the screen, every texel of it is at the same depth. That's exactly the property that made wall columns cheap in step 9: one scale factor for the whole sprite, and no perspective distortion to correct.

Our sprites are 64 × 64 texels, like the wall textures, and they are drawn exactly as tall as a wall: the bottom row stands on the floor and the top row touches the ceiling. Small objects leave most of the picture transparent. A lamp is a sprite whose few opaque texels are at the top; a barrel uses only the bottom half.

Where on screen: camera space again

Step 3 already did the hard part. For a sprite at world point q, the inverse camera matrix gives its camera coordinates: v, the depth in front of us, and u, the sideways offset in units of p.

function toCameraSpace(p, x, y) {
  const rx = x - p.x, ry = y - p.y;                       // q − pos
  const invDet = 1 / (p.planeX * p.dirY - p.dirX * p.planeY);
  return {
    u: invDet * ( p.dirY   * rx - p.dirX   * ry),
    v: invDet * (-p.planeY * rx + p.planeX * ry),
  };
}

Then it's the two divisions we've used all along. The sprite's centre lands on screen column screenX, and it's as tall as a wall at the same depth:

screenX = (W/2) · (1 + u / v)     size = projScale / v

The sprite is a square of side size, centred on screenX horizontally and on the horizon vertically. If v is negative the sprite is behind us. Step 3's Try this warned that without a check it would come out mirrored. If v is tiny, the sprite would be enormous, so anything nearer than a small NEAR_PLANE (0.2) is skipped.

Drawing it: columns with holes

A sprite is drawn the way a wall is: column by column, stepping through the texture with a fixed increment. Two things are new. The texture column is now also a linear function of the screen column, since the picture is flat and faces us. And a texel value of 0 means transparent, so we skip it and leave whatever is behind.

const step = TEX / size;                         // texels per screen pixel
for (let x = x0; x < x1; x++) {
  if (v >= zBuffer[x]) continue;                 // a wall is in front (next section)
  const texCol = ((x + 0.5 - left) * step | 0) * TEX;
  let texPos = (y0 + 0.5 - top) * step;
  for (let y = y0; y < y1; y++) {
    const color = img.pixels[texCol + (texPos | 0)];
    texPos += step;
    if (color !== 0) pixels[y * w + x] = color;  // 0 = transparent
  }
}

Zero works as “transparent” because every real colour from rgb() has its alpha byte set to 255, so no opaque pixel is ever 0. For each sprite we also store the first and last column that contains anything (img.left, img.right), and only loop over the screen columns in between. The empty margins of a lamp or a barrel cost nothing.

Behind walls: a depth buffer one row tall

A sprite behind a wall must not be drawn over it. A general 3D renderer keeps a depth value for every pixel. We can get away with one per column, because the wall pass draws exactly one wall slice per column, and the whole slice is at one depth. So while drawing walls we keep

zBuffer[x] = dist;   // the wall depth of column x

and each sprite column is drawn only if the sprite is nearer: v < zBuffer[x]. That's 320 numbers for the whole screen.

This is where step 7 pays off a second time. The wall depth and the sprite's v must measure the same thing for the comparison to make sense. DDA's t is the perpendicular depth, and so is v. If we had stored the Euclidean distance to the wall instead, it would be too large towards the screen edges, and sprites just behind a wall would poke through it at the sides of the view.

In front of each other: the painter's algorithm

The depth buffer only knows about walls. Sprites don't write to it, so when two sprites overlap on screen, the one drawn last wins. The fix is the oldest one in graphics: sort them by depth and draw the farthest first, the way a painter paints the background before the foreground.

visible.sort((a, b) => b.v - a.v);   // largest depth first

In general 3D graphics the painter's algorithm has a famous flaw: two polygons can each be partly in front of the other, and no order is right. Billboards can't do that. They are all parallel to the screen, each at a single depth, so they can never cut through each other, and sorting by v is always exactly right. We sort by v rather than by distance for the same reason: depth is what decides who covers whom.

  • Turn off the depth buffer: robots and barrels show through the walls in front of them.
  • Turn off sorting, then line up two sprites, for example the two barrels below the start corridor. Depending on where you stand, the far one is drawn over the near one.
  • Walk in a circle around a robot and watch the rotation frame in the readout. The picture snaps every 45°. That snapping is very Wolfenstein.
  • Show the sprite squares: every sprite really is a full square, as tall as a wall. Most of it is transparent.

Making the sprites

As with the textures, there are no image files. Every sprite is drawn by code in sprites.js at startup, out of a few simple shapes: balls, rods, cylinders and bevelled boxes. Each shape is shaded with the same idea: work out the surface's normal (the direction it faces) at each texel, and compare it with a light coming from the top-left, as with the bevels on the bricks.

For a ball of radius r, a texel at offset (nx, ny) from the centre (in units of r) is on the surface facing (nx, ny, √(1 − nx² − ny²)): the third part points towards the viewer. The brightness is a bit of ambient light plus the part that faces the light:

k = 0.38 + 0.8 · max(0, n · L)  (+ a small highlight)

A barrel is a cylinder whose radius bulges in the middle, with darker stripes for staves and hoops. The pillar's grooves, the lamp's cone and the plant's leaves are variations on the same few lines. Finally every sprite gets a dark one-texel outline, which keeps it readable against busy brick walls.

Eight directions

A barrel looks the same from every side; an enemy shouldn't. Wolfenstein's enemies have 8 pictures, one for every 45° around them, and the game picks the one that matches where you are standing.

Our robot is built from parts placed in its own little 3D space: X to its right, Z to its front, and Y the sprite row. To see it from angle θ (θ = 0 from the front, 90° from its right side), each part is rotated with step 2's rotation matrix:

column = 32 − X·cos θ + Z·sin θ     depth = X·sin θ + Z·cos θ

The parts are drawn far to near by that depth. It's the painter's algorithm again, this time inside one sprite. The backpack and antenna stick out behind it and the eye visor faces forward, so you can tell which way it faces. Drawing it at θ = 0°, 45°, …, 315° gives 8 sprites, and 4 walking poses for each direction give the walking robot 32 more.

At runtime, choosing the frame is one atan2: the direction from the robot to us, minus the direction the robot faces, rounded to the nearest 45°.

function rotationFrame(obj, p) {
  const toViewer = Math.atan2(p.y - obj.y, p.x - obj.x);
  const k = Math.round((toViewer - obj.angle) / (Math.PI / 4));
  return ((k % 8) + 8) % 8;     // 0 = it faces us, 2 = we're on its right, 4 = its back
}

Posts, spotvis and wallheight

Wolfenstein's sprites live in VSWAP next to the walls, in a format built for skipping transparency. Each sprite stores leftpix and rightpix (our left/right), and for every column in between a list of posts: runs of opaque texels, given as start row, end row and the texels themselves. The scaler draws each post with the same compiled scaling code as the walls and jumps over the gaps, so transparent texels aren't even visited.

The depth buffer is an array called wallheight[]. It holds each column's wall height on screen rather than its depth. Height is projScale / depth, so the test is the same one flipped: a sprite column is drawn if the sprite is taller than the wall there.

It also gets visibility nearly for free. While casting rays, every map tile a ray passes through is marked in a 64 × 64 table called spotvis. When it's time to draw sprites, objects in unmarked tiles (behind walls, out of view) are skipped without any maths. For moving enemies, which can straddle two tiles, the neighbouring tiles are checked too. The visible ones go into a list, and are drawn farthest first by picking the smallest one each time, a plain selection sort, which is plenty for a few dozen sprites.

Enemies have 8 rotation pictures for standing and walking. A function called CalcRotate picks one from the angle between the enemy's direction and the line to the player, exactly like rotationFrame.
