Part 4 · Step 18

BSP trees: front to back without sorting

Step 17 needed walls drawn near to far, and got that order from portals, which only works for convex sectors. Doom's answer is to do the sorting once, before the game even starts, and store the result in a binary tree. At run time, any viewpoint reads its front-to-back order straight off the tree, with one side test per branch.

One line splits the world

Pick any wall and extend it into an infinite line, a partition. It divides the level into two halves: in front of the line, and behind it. You're standing on one side of it, say in front. Here's the key fact: nothing behind the line can hide anything in front of it. The line of sight from your eye to any point on your side stays on your side (a half-plane has no dents), so nothing from the other side can get in its way. Things on your side, on the other hand, can certainly hide things on the far side.

So, to draw near to far: draw everything on your side of the partition first, then everything on the other side. That's not a full order yet, since each half can still contain a mess. But each half can be split again by another partition, and so on, until the pieces are simple enough that their order doesn't matter. Which pieces are those? Convex ones, step 17 told us: nothing in a convex piece can hide anything else in it.

Write the splits down as a tree. Each node holds a partition line and two children, the front half and the back half. Each leaf is a convex piece, a subsector, with its list of segs. Drawing near to far is then a short recursive walk:

function renderNode(node) {
  if (node.subsector) { drawSubsector(node.subsector); return; }   // convex: any order
  const side = pointOnSide(node, p.x, p.y);                        // 0 = we're in front
  renderNode(node.children[side]);                                 // our side first…
  renderNode(node.children[side ^ 1]);                             // …then the far side
}

Notice what doesn't happen at run time: no sorting, no distances, no comparisons between walls. The order changes as you move, because which child goes first at each node depends on where you stand, but the tree itself never changes.

Building the tree

The node builder starts with every seg of every sector, then:

  1. If the segs form a convex set (every seg is in front of every other seg's line), stop: this is a subsector.
  2. Otherwise choose a seg, and use the line through it as the partition.
  3. Sort every seg into front or back with pointOnSide on its two ends. A seg that lies on the partition line goes front if it faces the same way, back if not.
  4. A seg with one end on each side gets split in two at the crossing, with a brand-new vertex there. The crossing is at fraction t = a / (a − b) along the seg, where a and b are its ends' signed distances from the partition: the same interpolation as near-plane clipping in step 16. The second piece's texture offset grows by t · length, so its bricks still line up with the first piece's.
  5. Build the front set and the back set the same way.

Which seg makes a good partition? Every split adds a seg, which costs drawing time forever after, and a lopsided tree is deeper than it needs to be. Our builder tries every seg and scores it:

score = splits × 8 + |front − back|      // the lowest score wins

A seg with everything else on one side is skipped, because it doesn't divide anything. That can't happen for every seg unless the set is already convex, so the recursion always ends.

Walking it: solid segs

Step 17's clip arrays still decide which rows of a column are open. What the BSP walk adds is a cheaper way to know when a whole column is done. When a one-sided wall is drawn over columns a to b, nothing behind it will ever show there, and since we're going front to back, everything after it is behind it. Doom keeps a sorted list of these finished column ranges, the solid segs, and clips every seg against it before drawing:

clipSeg(a, b, solid, draw):
  for each gap in the list that overlaps [a, b): draw(that part)    // only the unfinished columns
  if (solid) merge [a, b) into the list                              // and now they're finished

Two-sided segs are clipped against the list too, but don't add to it. Their columns stay open through the gap. The list starts with two sentinel ranges, everything left of column 0 and everything right of the last column. When it has merged down to a single range, every column is finished and the walk can stop immediately, however much of the tree is left. Standing in a small room in a huge level, that's almost all of it.

Skipping whole branches

The walk can do even better. The node builder stores a bounding box for each child of a node, around all the segs below it. Before going into the far child, the walk checks whether any of its box could be visible. The box's outline from above is a rectangle, so clip it to the near plane and project its corners (step 16 again) to get the columns it spans. If those columns are off screen, or all inside one finished range, nothing in that branch can show, and the walk skips it without looking at a single seg.

Finding your sector

The tree answers step 15's “which sector am I in?” too. Start at the root and take the child on your side of each partition until you reach a leaf. Its subsector belongs to one sector. That's one side test per level of the tree, about 10 here, instead of a search through every linedef.

  • Replay a frame in the courtyard. The platform, which is nearest, goes in first, and the far wall last, filling only what's left. Step 17's concave courtyard is no problem any more.
  • Stand facing a wall up close and look at the counts: a handful of subsectors and the walk stops, because one wall finished every column.
  • Turn off “stop when the screen is full” and “skip boxes”: the picture is the same, but the walk visits every node in the tree.
  • In the first demo, watch the red rings: the node builder had to split some segs, mostly around the slanted pillar walls.

NODES, SSECTORS and SEGS

Binary space partitioning trees were invented for 3D graphics at the start of the 1980s, by Henry Fuchs, Zvi Kedem and Bruce Naylor, as a way to draw polygons in a correct order from any viewpoint. John Carmack first used one in a game in the Super Nintendo port of Wolfenstein 3D, which needed to be faster than ray casting on that console, and then built Doom around it.

The node builder ran when a level was saved and wrote three more lumps into the WAD: SEGS (the pieces of linedefs, each with its sidedef, direction and texture offset), SSECTORS (each subsector as a run of consecutive segs) and NODES (each a partition line as a point plus a direction, two bounding boxes, and two children; the top bit of a child number says “this is a subsector”).

The engine's walk is R_RenderBSPNode, almost line for line like renderNode. Its bounding box test, R_CheckBBox, works with view angles rather than projected corners. Segs go through R_ClipSolidWallSegment or R_ClipPassWallSegment, and the list of finished ranges is an array called solidsegs, with room for only 32 ranges. That's plenty, because the ranges merge as the screen fills up.

The tree is the reason for a famous limitation. Because it's computed in advance from the 2D map, the map can never change while you play. Floors and ceilings can move up and down (that changes heights, not lines), which is why every door in Doom is a ceiling that rises, and every lift a floor that lowers. But nothing can slide sideways or rotate, and no sector can be above another one.

Sprites aren't in the tree either. After the walls, Doom draws the visible things far to near, as in step 11, cutting each one off where a nearer wall covers it, using a record of every wall it drew.

Next

Walls are now right and nothing is drawn twice. Floors and ceilings, though, are still drawn one pixel at a time down each column, with a division for every pixel. Doom collects them into visplanes and draws them along rows instead, which is also where its lighting comes in.
