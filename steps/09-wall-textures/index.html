Part 2 · Step 9

Textured walls

Each wall column already has a position along the wall (where the ray hit) and a height on screen. Texture mapping is two small linear maps: one from the hit position to a texture column, and one from screen rows to texture rows. First, though, we need a texture.

Making bricks out of maths

Wolfenstein's textures are 64 × 64 pixels, and so are ours. Rather than shipping image files, we generate them at startup in textures.js. That keeps everything in code you can read and tweak, and it's a nice exercise in thinking per-texel.

A texel (short for “texture element”) is one pixel of a texture. The word keeps the two kinds of pixel apart: a texel lives in the 64 × 64 picture, a pixel lives on the screen. Drawing a wall means deciding, for every screen pixel, which texel to copy into it. Up close one texel covers many pixels; far away many texels share one pixel and most are skipped.

A texel at (u, v) (column, row) decides what it is from its coordinates alone:

  1. Which brick? Rows are 16 texels tall, so row = floor(v / 16). Every other row is shifted by half a brick (16 texels) to get the running-bond pattern: su = (u + shift) mod 64. Bricks are 32 wide, so inside the brick we're at bx = su mod 32, by = v mod 16.
  2. Mortar or brick? The first 2 texels of each brick cell (its top and left) are mortar. Each brick's mortar is shared with its neighbours, so this covers every gap.
  3. Emboss. Inside a brick, look at the distance to each of its four edges. Within 2 texels of the top or left edge the texel is brightened (×1.45). Within 2 texels of the bottom or right edge it's darkened (×0.55). Where two edges compete near a corner, the nearer one wins, which gives clean diagonal mitres like a real bevel. Light from the top-left plus a raised border is the oldest trick for making flat pixels look 3D.
  4. Variation. Each brick gets a random tint, and each texel a little noise, from a seeded random generator so the texture is the same every time.
function bevel(ix, iy, iw, ih, size, light, dark) {
  const dTop = iy, dLeft = ix, dBottom = ih - 1 - iy, dRight = iw - 1 - ix;
  const m = Math.min(dTop, dLeft, dBottom, dRight);
  if (m >= size) return 1;                          // brick face
  return (dTop === m || dLeft === m) ? light : dark; // lit edge or shadow edge
}

Three colour schemes give three wall types: grey stone, red brick and Wolfenstein's iconic blue stone. Each is makeBrickTexture(base, mortar, seed) with different inputs.

u: which texture column

DDA told us which grid line we hit, and the hit point is pos + t·rayDir. If we crossed a vertical line (side = 0), the wall face runs along y, so the position along it is the hit's y coordinate. On a horizontal line it's the x coordinate. We only want the part inside the cell:

let wallX = hit.side === 0 ? p.y + hit.t * rayDirY : p.x + hit.t * rayDirX;
wallX -= Math.floor(wallX);                 // 0 … 1 across the face
let texX = Math.floor(wallX * TEX);         // 0 … 63
if ((hit.side === 0 && rayDirX < 0) || (hit.side === 1 && rayDirY > 0)) texX = TEX - 1 - texX;

The flip on the last line is easy to miss. Facing east, your right hand points to +y, so wallX grows left-to-right on screen. Facing west, your right hand points to −y, so it grows right-to-left and the texture would be mirrored. Same for north versus south. (With symmetric bricks you'd barely notice; with text or an arrow on the wall you would.)

v: screen rows to texture rows

The wall occupies screen rows from wallTop to wallTop + lineHeight, and those rows should show texture rows 0 to 64. That's a linear (affine) map:

texY = (y − wallTop) · (64 / lineHeight)

Since y goes up by 1 per pixel, texY goes up by a constant step = 64 / lineHeight. So instead of a multiply per pixel we add step, a pattern that shows up everywhere in software rendering:

const step = TEX / lineHeight;
let texPos = (top + 0.5 - wallTop) * step;   // start at the first VISIBLE row's centre
for (let y = top; y < bottom; y++) {
  const texY = (texPos | 0) & (TEX - 1);
  texPos += step;
  pixels[y * w + x] = tex[texX * TEX + texY];
}

Note top versus wallTop. When you stand close to a wall, wallTop is negative (the wall extends above the screen), and we clip to row 0. Starting texPos at the clipped row, not at 0, is what keeps the texture from sliding around as you approach.

Why is a linear map correct here, with no perspective correction? Because a wall column is vertical in the world, every point in it is at the same depth. Perspective only distorts things whose depth varies. Walls in columns and (next step) floors in rows are exactly the two directions of constant depth, and that's why this whole engine design is so cheap.

Why column-major

The texture array is stored column by column: texel (u, v) lives at u * 64 + v. The inner loop reads one column top to bottom, so its reads are consecutive in memory. That made a big difference on a 386 with tiny caches; in JavaScript it mostly keeps the index maths simple.

  • Walk right up to a wall: step drops below 1 and each texel covers several pixels. Back away: step exceeds 1 and texels get skipped, so distant walls shimmer as you move. (Wolfenstein shimmered too. Mipmapping came later.)
  • Turn on the coordinate colours. Red increases left to right on every face, whichever direction you look from. That's the flip doing its job.

Palettes, posts and VSWAP

Wolfenstein's walls are 64 × 64 bytes each: palette indices into the game's 256-colour VGA palette, not RGB. They live in a file called VSWAP, stored column-major for exactly the reason above, since the compiled scalers from step 6 read one 64-texel column and stretch it to the column height.

There is no shading code at all. Every wall texture exists twice in the data, a light version for one orientation and a hand-drawn darker version for the other, and the renderer simply picks one. We fake it with shade(), which halves the RGB channels.

Being palette-based also made a classic effect cheap: changing palette entries recolours the whole screen instantly. Wolfenstein's red flash when you get hurt and the gold flash when you grab treasure are palette shifts, not pixel work.
